# Encryption coverage audit (Ref 2 Stage 3)

**Date:** 2026-09-30 · **Branch:** `version2` · **Scope:** every value BeamOS
itself persists that could act as a credential or secret, and how each one is
protected at rest by application code.

This is the working record behind [encryption.md](encryption.md). It lists
what was checked and why each item got the verdict it did. It also covers the
one gap that was found and fixed.

## Method

1. Every column in [`server/db/schema.sql`](../server/db/schema.sql) whose
   name matches `secret|key|token|password|pass|hash|credential|otp|pin|salt|cert|signature|webhook|api_|private|recovery|code`
   was listed. For each hit, the code that reads and writes it was traced.
2. Searched for tables created outside `schema.sql`. There are none: every
   `CREATE TABLE` in application code is in `schema.sql`, which
   `db/database.js` applies on every boot.
3. Checked `app_settings` (the only generic key/value store). It holds three
   operational settings: `status_debug_enabled`,
   `reconciliation_frequency_days` and
   `pending_installation_report_frequency_days`. None are secrets.
4. Every secret-shaped `process.env` value in
   [`server/config.js`](../server/config.js) was listed. The code was then
   searched to confirm none of them is ever written to the database.

## Verdicts: database columns

| Column | What it is | At-rest form | Verdict |
|---|---|---|---|
| `users.password_hash` | Login password | bcrypt, cost 10 (`routes/auth.js`, `routes/admin.js`) | ✅ Correct. A slow salted hash is the right tool for a low-entropy password. |
| `users.totp_secret_enc` | TOTP seed (#100) | AES-256-GCM via [`lib/secretbox.js`](../server/lib/secretbox.js) | ✅ Correct. The server must re-derive codes, so this has to be reversible encryption rather than a hash. |
| `totp_recovery_codes.code_hash` | One-time MFA recovery codes | SHA-256 (`lib/totp.js` `hashRecoveryCode`) | ✅ Correct. These are only ever verified. |
| `ai_settings.api_key_enc`, `ai_settings.image_api_key_enc` | Customer's own AI provider keys (#41) | AES-256-GCM via secretbox | ✅ Correct. They must be decrypted to call the provider. |
| `api_tokens.token_hash` | `st_` API tokens | SHA-256 | ✅ Correct as-is, untouched. See the note below. |
| `scim_tokens.token_hash` | `scim_` SCIM bearer secrets (Ref 8) | SHA-256 | ✅ Correct as-is, untouched. |
| `entra_service_principals` | Ref 9 SP registrations | **No secret stored.** Only `client_id` (a public GUID). | ✅ Nothing to protect. Each call carries an Entra-issued token checked by `jwtVerify`. |
| `activity_log.prev_hash` / `entry_hash`, `activity_log_chain.last_hash` | Ref 17 tamper-evidence chain | SHA-256 digests | ✅ Integrity values, not secrets. |
| **`devices.device_token`** | **Each screen's long-lived bearer credential** | **Was plaintext** → now `sha256:<hex>` | ❌→✅ **The one real gap. Fixed in this stage.** See below. |
| `devices.pairing_code` | Code the screen shows so an admin can claim it | Plaintext | ✅ Acceptable. It's generated by the device and **shown on the screen itself**, so hashing it would protect nothing. It only claims an *unclaimed* device. |
| `registration_codes.code` | 6-digit advance activation code (Ref 30) | Plaintext | ✅ Acceptable. It's single-use with a TTL (`expires_at`), and admins must be able to see it in the dashboard list to hand it to an installer, so it can't be one-way hashed. Its worth to an attacker ends when it's claimed or expires. |
| `white_labels.*` | Branding (name, colours, logo URL, custom CSS, domain) | Plaintext | ✅ Not secret. |

**Why hash and not secretbox for bearer tokens.** A value the server only
needs to **verify** is stored as a one-way hash. A database or backup leak
then yields nothing usable, because there is no key to steal alongside it.
Reversible encryption (secretbox) is only for values the server must read
back in plaintext: TOTP seeds and outbound AI keys. `api_tokens`,
`scim_tokens`, recovery codes and now `device_token` fall in the first group.
A plain unsalted SHA-256 is right for them because each is ≥ 256 random bits.
Brute-forcing the preimage is not a real threat, unlike with a password.

## The gap: `devices.device_token` (fixed)

**What it was.** A 256-bit random token minted at first pairing, at
activation-code claim ([`routes/registration-codes.js`](../server/routes/registration-codes.js))
and at fingerprint reclaim ([`ws/deviceSocket.js`](../server/ws/deviceSocket.js)).
The device presents it on every socket reconnect. The server stored it
**verbatim** and compared it with `timingSafeEqual`. Anyone who could read
the `devices` table, or a mysqldump of it, could connect as any screen in
the fleet.

**What changed** ([`lib/device-token.js`](../server/lib/device-token.js)):

- Every write stores `hashDeviceToken(raw)` = `'sha256:' + SHA-256(raw)`.
  The prefix distinguishes a hashed row from a legacy one, since both would
  otherwise be 64 hex characters.
- `validateDeviceToken` accepts **both** a hashed row and a legacy
  plaintext row, in constant time.
- The reconnect path used to echo the **stored** token back in
  `device:registered`. It now echoes the token the device **presented**,
  which is identical because it just passed verification. So the server
  never needs its own plaintext copy, and **no player change is needed**.
  Devices keep the token they already hold. This echo change is
  **load-bearing**. All three players overwrite their saved token with
  whatever `device:registered` carries:
  - Android: `WebSocketService.kt`, `config.deviceToken = data.optString("device_token")`
  - web: `server/player/index.html`, `config.deviceToken = data.device_token`
  - Tizen: `tizen/js/app.js`, `deviceToken = data.device_token`

  Echoing the stored value would have made every screen save the **hash**,
  present it on the next reconnect and be locked out. The real-socket test
  "the SAME token is echoed back" guards this.

**Migration plan for existing rows.**
[`server/scripts/hash-device-tokens.js`](../server/scripts/hash-device-tokens.js)
follows `scripts/migrate-sqlite-to-mysql.js`'s safe-migration pattern:

```bash
node server/scripts/hash-device-tokens.js --dry-run   # counts only, writes nothing
node server/scripts/hash-device-tokens.js --yes       # snapshot `devices`, then hash plaintext rows
```

- **No silent upgrade on authentication.** Deploying the code alone only
  hashes *new* tokens. The existing fleet stays in plaintext until an
  operator runs the script. This keeps the irreversible step explicit and
  reviewable.
- It is idempotent: already-hashed rows are skipped. Each `UPDATE` is
  compare-and-set on the old value, so a token re-issued mid-run (a
  fingerprint reclaim) is never overwritten.
- Before writing it takes a table-scoped `mysqldump` snapshot of `devices`
  (skip it with `--no-snapshot`). **That snapshot contains the plaintext
  tokens.** It lands in the gitignored `server/db/backups/` folder. Delete it
  or move it to secured storage once the rollout is confirmed. Leaving it on
  disk keeps exactly the exposure the migration removes.
- **Rollback caveat.** Code older than this change compares plaintext and
  cannot verify a hashed row. After hashing, downgrading past this commit
  locks those devices out until they are re-paired or the snapshot is
  restored. #143 made an invalid token a lockout, not a re-provision.
- **Dry run on the dev database (2026-09-30):** 323 devices, 316 plaintext,
  3 already hashed (made by the new tests), 4 without a token. `--yes` was
  **not** run against the dev database. That is an operator decision.

**Evidence.** [`server/test/device-token.test.js`](../server/test/device-token.test.js)
has 11 tests:

- Units for the hash format and dual-form verification.
- Backfill tests on an in-memory database: dry-run writes nothing, `--yes`
  keeps the same raw token verifying, the script is idempotent, and it is
  compare-and-set. It never touches the real database, because the backfill
  is irreversible.
- A **real `server.js` subprocess with a real socket.io device client.** The
  checks:
  - First pairing stores only the hash.
  - Reconnecting with the raw token works, and the same token is echoed back.
  - Presenting the stored *hash* is refused, so a leaked row is useless.
  - A wrong token is refused.
  - A legacy plaintext row still authenticates and is **not** rewritten.

  On the unmodified code the at-rest assertions fail, which confirms they
  catch the gap.

## Verdicts: configuration secrets (not in the database)

Every deployment secret is read from the process environment in
[`server/config.js`](../server/config.js):

- `JWT_SECRET`
- `DATA_ENCRYPTION_KEY` (Stage 2)
- `MYSQL_PASSWORD`
- `STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET`
- `GRAPH_CLIENT_SECRET` (+ tenant/client IDs)
- `ENTRA_TENANT_ID` / `ENTRA_API_CLIENT_ID` / `SSO_TENANT_ID` /
  `MICROSOFT_CLIENT_ID` / `GOOGLE_CLIENT_ID` (identifiers, not secrets)
- `DATA_PLATFORM_S3_ACCESS_KEY_ID` / `DATA_PLATFORM_S3_SECRET_ACCESS_KEY`
- `SSL_KEY` (a path to the private key file)

The code was searched for every use of these values. They reach only their
SDK or client: `stripe(...)`, `S3Client`, the Graph mailer, `jwt.verify`,
and `mysqldump` via `MYSQL_PWD`. **None is ever written to the database.**
This is the 12-factor pattern and standard practice, not a gap. Protecting
them is the job of the deployment's secret store: Key Vault/Secrets Manager
references, container secrets, or file permissions.

Two caveats, documented rather than changed:

- **`JWT_SECRET` fallback file.** If `JWT_SECRET` is unset, a random secret
  is generated once and stored in `<CERTS_DIR>/.jwt_secret` on disk. That
  file is itself a secret at rest. It is protected only by filesystem
  permissions and the disk's own encryption. Production should set
  `JWT_SECRET` from its secret store.
- **The TLS private key** (`SSL_KEY`, when BeamOS terminates TLS itself) is a
  PEM file on disk, with the same caveat.

## Related, out of scope for at-rest encryption

- **Field-technician OTP (Ref 43) stores nothing, but it is a fixed
  placeholder code (`000999`) in [`routes/field-auth.js`](../server/routes/field-auth.js).**
  This isn't an encryption issue. It's an authentication placeholder the
  Ref 43 docs already call out. It must be replaced with a real per-request
  code before field login is exposed. It is listed here so the audit doesn't
  look as if it missed it.
- **Everything else in the database is plaintext at the application layer**:
  content metadata, telemetry, tickets, proof-of-play, users' names, emails
  and phones. Protecting it relies on database or disk encryption, an
  infrastructure control. See [encryption.md](encryption.md).
